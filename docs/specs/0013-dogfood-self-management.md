# Spec 0013: Dogfood — VibeConform manages VibeConform

Status: proposed.

## Problem

`docs/plans/0001-bootstrap.md` set out a four-step sequence: bootstrap
guardrails by hand, build the tool, migrate this repository onto it, and
have VibeConform become its own first dogfood repository. Steps 1 and 2 are
done. Steps 3 and 4 are this spec, and they are what closes M1.

Until they happen, every managed file exists twice — live in the repository,
and embedded in a module — with only a test asserting they agree. The
duplication is the whole reason to finish: the templates are hypotheses
about what a conformant repository looks like, and nothing has tested them
against a real one.

## Scope

1. **`vibe.yaml`**, committed at the repository root:

   ```yaml
   standard: production
   version: v1
   ```

2. **`.vibe/state.yaml`**, generated by running `vibe sync` and committed.
   Machine-owned bookkeeping, but tracked: without it, every clone and every
   CI run reconciles two-way and cannot distinguish drift from conflict.

3. **A `task audit` target** in `Taskfile.yml`'s template, running the CLI
   against this repository, added to `verify`'s step list:

   ```yaml
   audit:
     desc: Check this repository against the standard it declares.
     cmds:
       - go run ./cmd/vibe audit --repo-root .
   ```

4. **A `conformance` CI job** in the `ci.yml` template, running `task audit`.
   Landed in two steps (see below).

5. **`AGENTS.md`**: a rule stating that managed files must be changed
   through their module template plus `vibe sync`, never edited directly.

Changes 3 and 4 are made to the **templates** in `internal/module/...`, then
adopted into the live files by running `vibe sync`. Editing the live files
directly would be non-conformant the moment it lands.

## Behavior

### Acceptance test for the whole milestone

After `vibe sync` runs on this repository for the first time, `vibe audit`
must report every resource `ok` and exit 0 — on a repository whose files
were written by hand months earlier.

That is the real test of increments 0010–0012. If any resource reports
`drifted` or `conflict`, a template diverged from the file it was seeded
from, and the difference is the finding: either the template is wrong, or
the live file drifted and the template is right. Resolve it explicitly in
this increment's PR; do not "fix" it by re-seeding the template from
whatever the live file happens to contain.

### Two-step CI adoption

- **Step A (this spec):** the `conformance` job runs `task audit` with
  `continue-on-error: true` and is *not* in the `gate` job's `needs` list.
  One merged PR's worth of real output on real runners, gating nothing.
- **Step B (follow-up PR, same increment):** remove `continue-on-error`, add
  `conformance` to `gate`'s `needs`. Conformance becomes required.

A gating self-audit introduced in the same PR as the modules it validates
can lock the repository out of its own CI with no green path back. The
branch-protection check is named `CI / gate`, and that name does not change
in either step — only what `gate` waits for.

### Ordering inside the run

`task audit` runs `go run ./cmd/vibe`, so it compiles the tool before
auditing. In CI the `conformance` job therefore needs Go set up like every
other job, and is only meaningful if the code compiles — which `typecheck`
already establishes independently.

## Explicit non-goals

- **No `release.yml` or `.goreleaser.yaml` management** (spec 0010's
  non-goal). After this increment they remain the only hand-maintained
  files under `.github/`, and `docs/usage.md` says so rather than implying
  `.github/` is fully managed.
- No branch-protection or repository-settings management. `vibe` writes
  files in a working tree; it does not call the GitHub API. See
  `PUBLIC_REPO_CHECKLIST.md` for what is configured by hand and why.
- No `vibe sync` in CI, ever. CI audits; it never writes. A CI job that
  syncs and commits would make the gate unfalsifiable.
- No removal of the hand-written guardrails this repository already has —
  they become *outputs* of the modules, not deletions.
- No `vibe check`/`doctor`, no affected-component graph — M2.

## Design notes

- `.vibe/` is not gitignored, so `state.yaml` is committed by default. Worth
  confirming rather than assuming: the file's absence from git is what
  silently degrades reconciliation to two-way.
- Committing `.vibe/state.yaml` means a PR that changes a template shows
  two diffs: the template and the resulting state hash. That is a feature —
  the hash change is the reviewable evidence that the managed file changed.
- From this point on, this repository cannot change a managed file without
  changing a module. That is the intended constraint, and it is also the
  main cost of the milestone: routine edits to `Taskfile.yml` or `ci.yml`
  get slower. The `AGENTS.md` rule exists so the constraint is discovered by
  reading, not by a failing CI job.
- This repository becomes the standard's only real conformance evidence
  until a second repository adopts `production/v1`.

## Follow-on work (M2)

- A second dogfood repository, which is the first real test of whether
  `production/v1` is a standard or just a description of this repository.
- Affected-component graph and `vibe check`.
- `vibe doctor`.
- Parameterization and conditionality in standards — the constraints
  increments 0010–0012 kept hitting.
- `StructuredPatch`/`ManagedSection` ownership, first demanded by
  `.claude/settings.json` (spec 0012's follow-on).
