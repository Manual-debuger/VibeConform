# Spec 0037: Declared Generated-Code Paths

Status: draft. Builds on spec 0025 (`prod-mono/v1`), ADR 0012
(`components:`), spec 0029 / ADR 0014 (managed sections) and spec 0026
§10 (Prettier exclusions for owned editor files).

## Problem

Adopters commit code that a generator writes from a schema. The managed
lint and format configurations treat it as hand-written code, and the
repository cannot tell them otherwise. Those files are generated whole by
VibeConform (`ruff.toml`, `eslint.config.js`), so a hand-added exclude
makes the repository non-conformant and fails `vibe audit`.

The case behind this spec is a `prod-mono/v1` repository that turns one
set of JSON Schemas into committed types for three components:

| Component | Generator | Output |
|---|---|---|
| `api` (go) | in-house, header `// Code generated ... DO NOT EDIT.` | `services/api/internal/contracts/contracts.gen.go` |
| `worker` (py) | `datamodel-codegen` (pydantic) | `services/worker/src/worker/contracts/*.py` |
| `web` (ts) | `json-schema-to-typescript` | `apps/web/src/contracts/*.ts` |

Today the adopter post-formats generated output with ruff and prettier so
that `fmt:check` and `lint` pass. Their generator pipeline therefore
depends on the repository's style configuration. Every time the standard
adds a lint rule, they find out by regenerating.

## Constraints

- **Principle 1.** The exclusion is rendered into the tools' own
  configuration, so every entry point honours it the same way:
  `task`, lefthook, the agent hooks, CI and the editor. It is never a
  sentence in `AGENTS.md`.
- **"A check that silently covers less is worse than one that fails."**
  This is the eslint template's own comment. An exclusion must be
  declared, visible in review, and bounded. A typo must never be able
  to exclude a whole component.
- **Principle 2.** The same bytes and the same behaviour on Windows and
  Linux. Globs are slash-separated.
- **Principle 3.** What is rendered is ordinary tool configuration
  (`extend-exclude`, `ignores`, `.prettierignore`). It keeps working
  after VibeConform is removed, and nothing in `task verify` calls
  `vibe`.
- **Backward compatibility.** A `vibe.yaml` without the new key resolves
  every resource of every standard byte-for-byte as today. Spec 0025's
  "no generated byte changes for existing adopters" holds.
- **ADR 0012.** Decoding stays strict. A field that nothing reads is not
  added, so a profile on which the key would have no effect rejects it.
- **ADR 0003 / 0014.** VibeConform owns whole files, or sections between
  markers. It never edits lines outside them.

## Assumptions

Each assumption below is checked by a probe before implementation (plan
step 0). If one is false, this spec is revised; the code is not quietly
adapted.

- A1. Ruff's `extend-exclude` patterns are relative to the directory of
  the `ruff.toml` that sets them. A pattern containing `/` is anchored
  there. `*` does not cross `/`, and `**` does. With
  `force-exclude = true`, files passed explicitly are skipped too (the
  ruff settings docs say so). Ruff exits 0 when every file it is given
  is excluded.
- A2. ESLint flat-config global `ignores` are relative to
  `eslint.config.js`. A pattern without a trailing `/` matches files and
  directories (the ESLint docs say so). A file passed explicitly that a
  pattern ignores gives a warning, which `--no-warn-ignored` suppresses,
  and exit code 0.
- A3. Prettier 3 reads `.prettierignore` (gitignore syntax) from its
  working directory, and skips an ignored file even when it is passed
  explicitly, with exit 0 for both `--check` and `--write`.
- A4. golangci-lint v2 skips Go files that follow the generated-file
  convention by default. The configuration reference says
  `linters.exclusions.generated` defaults to `strict` ("strictly
  following the Go generated file convention") and
  `formatters.exclusions.generated` to `lax`. The managed
  `.golangci.yml` sets neither, so the defaults apply. `gofmt -l` and
  `goimports -l` do not skip generated files.
- A5. Every generator in the adopter's case writes its output under a
  directory, or to a file, at a fixed path. None of them writes next to
  hand-written files under a name that only a pattern like `**/*.py`
  could select.

## Desired Behavior

### 1. Declaring generated paths

A component may list the files a generator owns:

```yaml
components:
  - id: worker
    path: services/worker
    profile: py
    generated:
      - src/worker/contracts/**
  - id: web
    path: apps/web
    profile: ts
    generated:
      - src/contracts/*.ts
```

A single-language standard has the same thing as a top-level key,
relative to the repository root:

```yaml
standard: prod-py
version: v1
generated:
  - src/example/contracts/**
```

- In `prod-mono`, a top-level `generated:` is an error naming the
  component form. In a single-language standard, `generated:` under a
  component is impossible already, since `components:` is rejected.
- An absent key and an empty list resolve the same: nothing changes.
- **Go rejects the key**, for `profile: go` and for `prod-go`. The error
  points to the `// Code generated ... DO NOT EDIT.` header. That header
  is Go's own convention (`go/ast.IsGenerated`), and golangci-lint
  already honours it (A4). Accepting the key would add a second
  mechanism for what Go already has, and on Go it would change nothing
  but the linter. See §3 for why `gofmt` still applies.

### 2. Glob grammar and validation

Each entry is a pattern that matches files (or, written as `dir/**`, a
directory's contents) relative to the component, or to the root in a
single-language standard. `vibe.yaml` is rejected with exit 1, before
anything resolves, unless every entry satisfies all of the following:

| Rule | Rejected example |
|---|---|
| non-empty, no whitespace | `""` |
| forward slashes only | `src\gen\*.py` |
| relative: no leading `/`, no `:` | `/src/gen`, `C:/gen` |
| already clean: `path.Clean` leaves it unchanged, so no `./`, `//`, trailing `/` | `./src/gen/*.py`, `src/gen/` |
| no `..` segment, and not `.` | `../shared/gen.py`, `src/../x` |
| at least two segments, and the first one is literal (no `*`) | `contracts.py`, `*/gen.py`, `**/*.py`, `**` |
| each segment uses only `A-Z a-z 0-9 . _ -` and `*`; `**` only as a whole segment | `src/gen/[a-z].py`, `src/{a,b}/x.ts`, `!src/gen`, `src/gen/**.py` |
| unique within its list | |

The first-literal-segment rule anchors every pattern to a named
directory of the component. It is what stops a typo from excluding the
whole component, and it gives one meaning across the tools: in ruff and
in gitignore syntax, a single-segment pattern would otherwise match at
any depth. The character set excludes every metacharacter on which
ruff, minimatch and gitignore disagree. It also excludes every character
that would need escaping in TOML, JavaScript or a `.prettierignore`
line.

Patterns stay inside the component by construction (relative, clean, no
`..`). They are not checked against the filesystem. Resolution is a
function of `vibe.yaml` alone (the determinism contract of
`module.Module`), and a pattern that matches nothing excludes nothing.

### 3. What a declared path is excluded from

The rule: **checks whose findings are fixed by editing the file are
skipped (format and lint). Checks that judge whether the program is
correct still run (compile, typecheck, test).** A generated file is
fixed by changing the generator or the schema, never the file, so a
style finding on it is not actionable. A type error in it is a real
defect in the contract that every consumer imports.

| Profile | Format | Lint | Typecheck |
|---|---|---|---|
| py | excluded: `ruff.toml` `extend-exclude` + `force-exclude = true` | excluded: the same keys | **still checked** (`pyrightconfig.json` unchanged) |
| ts | excluded: managed section in `.prettierignore` | excluded: `eslint.config.js` global `ignores` | **still checked** (`tsc`; `tsconfig.json` is the project's) |
| go | key rejected (§1); `gofmt`/`goimports` still apply | skipped by header (golangci default, A4) | **still checked** (`go build`, `go vet`) |

Why formatting is excluded for Python and TypeScript, but Go stays
`gofmt`-clean:

- Ruff and Prettier styles are configured per repository (quotes, line
  length, semicolons). A generator cannot know them. Requiring
  generated output to match them couples every generator to this
  repository's configuration, which is the reported problem.
- `gofmt` has one style and no configuration. Go generators emit it
  through `go/format` by convention. Requiring it costs nothing, and the
  check keeps covering every file. `gofmt -l .` also has no exclude
  option, so exempting files would mean replacing it with a file walk.

The exclusion takes effect at every entry point that runs the tool:

- `task fmt`, `fmt:check`, `lint` and `verify`;
- `fmt:changed` (the agents' `hook:format`) and `hook:check`;
- lefthook pre-commit, where files are passed explicitly. This is why
  ruff gets `force-exclude` and why the ESLint pre-commit command of
  `prod-ts` gets `--no-warn-ignored` when paths are declared: a commit
  touching generated code neither fails nor warns;
- editors that read the same configuration files.

### 4. Rendered output

Shown for the example in §1. Exact comment wording is the plan's.

- Python, `<component>/ruff.toml`: two top-level keys before `[lint]`,
  with a comment naming `vibe.yaml` as the source:
  `extend-exclude = ["src/worker/contracts/**"]` and
  `force-exclude = true`.
- TypeScript, `<component>/eslint.config.js`: the patterns are appended
  to the existing global ignores object, after `'**/dist/**'` and
  `'**/coverage/**'`.
- TypeScript, `<component>/.prettierignore`: a managed section
  `generated` (hash-comment markers, placed at the bottom), holding one
  line per pattern. Lines outside the markers stay the project's, and
  the file is created when it is absent.

`.prettierignore` is a managed section rather than a generated file,
because adopters already keep their own ignore lines there. It is
preferred over negated CLI globs (the spec 0026 §10 mechanism), because
Prettier reads it at every entry point, editors included. Spec 0026
§10's exclusions for editor files are unchanged.

### 5. Changing or removing the declaration

- Editing the list re-renders the files. Whole files update as usual,
  and the section updates three-way.
- When the list becomes empty or is removed, or the component is
  removed, a recorded `generated` section is removed under the rules for
  a deselected option's section (spec 0026 §7). It is removed when
  unmodified, and kept as a conflict when modified. A file that held
  only the section is deleted. A stale ignore list must not survive the
  declaration it came from: it would be exactly a check covering less
  without anyone saying so.

### 6. Visibility

`vibe diff` already shows each changed managed file. In addition,
`docs/usage.md` documents the key, the grammar, the table in §3, and
how to keep generated code current. That last part is a `Taskfile.local.yml`
task that regenerates and runs `git diff --exit-code`. VibeConform does
not run generators.

## Non-goals

- **Running or checking generators.** Whether committed generated code
  matches its schema is the repository's check (`Taskfile.local.yml`),
  not the standard's.
- **Header detection for Python and TypeScript** (the counter-design).
  Ruff, ESLint and Prettier have no generated-header detection, so
  honouring headers would mean `vibe` reading file contents and listing
  files at sync time. That makes the resolved output depend on
  repository contents (against `module.Module`'s determinism contract:
  same `vibe.yaml`, same resources), and it still needs
  rendering into the same excludes. Headers stay the mechanism for Go
  only, where the tools already implement them.
- **Excluding generated code from type checking or tests.** See §3.
  `pyrightconfig.json` and `tsconfig*.json` are unchanged.
- **A per-tool exclusion list** (lint but not format, or the reverse).
  One list, one meaning.
- **Arbitrary excludes** ("ignore this hand-written legacy module").
  The key is named `generated` and the grammar is narrow on purpose.
  Excluding hand-written code is a different decision, with a different
  review bar.
- **`vibe doctor` checks on the patterns** (matching nothing, or
  matching a file without a generated header). They are a possible
  follow-on, listed in the plan's open questions.

## Acceptance Criteria

Unit tests unless marked otherwise.

- [ ] AC1. **Backward compatibility.** For each of `prod-go`, `prod-ts`,
  `prod-py` and `prod-mono`, a manifest without `generated:` and one
  with `generated: []` (top-level, or on every component) resolve
  byte-identical resources, in the same order, as the unmodified
  manifest. Every committed example and this repository stay
  conformant without re-syncing (`TestExamplesAreConformant`,
  `task audit`).
- [ ] AC2. **Parsing.** `manifest.Parse` accepts each valid form in §1
  and §2 (`src/a/*.py`, `src/a/**`, `src/**/gen/*.ts`, `src/a.gen.ts`),
  and rejects each rejected example in §2's table, plus a duplicate,
  with an error naming the component id and the index of the offending
  entry. Unknown keys under a component are still rejected.
- [ ] AC3. **Standard checks.** `generated:` on a `profile: go`
  component, top-level under `prod-go`, and top-level under
  `prod-mono` are each a plan error before anything resolves (exit 1),
  naming the header convention or the component form respectively.
- [ ] AC4. **Rendering, Python.** With `generated` declared, the
  component's (or root's) `ruff.toml` differs from the template only by
  the `extend-exclude` and `force-exclude` keys of §4, in declaration
  order. It parses as TOML, and both keys are top-level.
  `pyrightconfig.json` is byte-identical to the template.
- [ ] AC5. **Rendering, TypeScript.** `eslint.config.js` differs from
  the template only by the appended patterns in the global ignores, in
  declaration order. `.prettierignore` holds a `generated` section with
  one line per pattern. The single-language `prod-ts` `lefthook.yml`
  ESLint command gains `--no-warn-ignored`, and nothing else in
  `lefthook.yml` or `Taskfile.yml` changes. `tsconfig.base.json` and
  `.prettierrc.json` are byte-identical to the templates.
- [ ] AC6. **Sections.** A `.prettierignore` with user lines keeps them
  byte-for-byte after sync. An absent one is created. Emptying the list
  removes an unmodified section (and a file that held only that
  section), and keeps a modified one as a conflict. Removing the
  component does the same.
- [ ] AC7. **Tool behaviour (integration, CI).** `examples/monorepo`
  declares `generated:` for `web` and `worker`, and commits a generated
  file in each that fails Prettier/ESLint and ruff format/lint
  respectively, but type-checks. `examples.yml` runs `task verify`,
  `task verify:fast` and `task hook:format` there and they pass on
  Ubuntu and Windows. A test in the same job shows that a non-generated
  file with the same content still fails, so the check did not stop
  covering everything.
- [ ] AC8. **Explicit files.** The probe of plan step 0, kept as a
  documented manual check, shows that `ruff format --check`,
  `ruff check`, `prettier --check` and `eslint`, each given a declared
  generated file explicitly (as lefthook and `fmt:changed` do), exit 0
  with no finding and no warning.
- [ ] AC9. **Go.** The probe confirms A4 for the pinned golangci-lint:
  a file with the standard header and a lint finding passes
  `golangci-lint run` with the managed `.golangci.yml`, and a
  non-`gofmt` generated file fails `fmt:check`. `docs/usage.md` states
  both.
- [ ] AC10. **Verification independence.** No rendered change makes
  `task verify`, `verify-ci`, lefthook or CI reference `vibe` (the
  existing spec 0017/0022 tests pass unchanged).
- [ ] AC11. **Docs.** `docs/usage.md` covers the key, the grammar, the
  §3 table, the Go header rule, removal, and the regenerate-and-diff
  pattern. ADR 0012's field table is amended by a new ADR.
