# Spec 0044: One Pin Table for Generated CI, and a GitLab Schema Check

Status: accepted and implemented (2026-10-08); CI on the pull request
and a real GitLab run (issue #74) outstanding. Implementation plan:
`docs/plans/0044-ci-pin-table.md`. Pinning
`actionlint` together with `goimports` and `govulncheck` was confirmed
with the user, along with bumping the tool pins whenever `GO_VERSION`
is bumped. First of five specs that simplify the generated CI for
adopting repositories (settled with the user on 2026-10-07). The other
four, in order:
- per-provider partials with GitLab `extends:`
- single-language standards as one implicit component
- environment seams
- skipping unchanged components on GitLab

Real GitLab runs are deferred to issue #74.

## Problem

The toolchain versions in generated CI are literals, copied into every
template that needs them:

| Pin | Templates |
|---|---|
| `GO_VERSION` | 7: `ci/github`, `ci/githubpy`, `ci/githubts`, `ci/githubmono`, `ci/gitlabmono`, `conformance.yml`, and `gitlab-ci.vibe.yml` (as the `golang:1.27.0` image) |
| `TASK_VERSION` | the same 7 |
| `GOLANGCI_LINT_VERSION` | 3 |
| `NODE_VERSION`, `PYTHON_VERSION` | 3 each |
| `TASK_SHA256` (must change together with `TASK_VERSION`) | `ci/gitlabmono` only |

Only `TestVersionsMatchGitHub` cross-checks these, and it covers
`gitlabmono` against `githubmono` and nothing else. A bump that misses
one file ships without any test failing, so different CI files in one
adopting repository can end up on different toolchains.

Some tools are installed `@latest` instead of pinned:
- `goimports` (`ci/github`, `ci/githubmono`, `ci/gitlabmono`)
- `govulncheck` (the same three)
- `actionlint` (`ci/github`, `ci/githubmono`)

Two runs of the same commit can install different tool versions and
reach different verdicts.

Nothing checks that GitLab accepts the generated GitLab CI. The
`monorepo-gitlab` job in `.github/workflows/examples.yml` proves only
that `vibe sync`, `task verify` and `task audit` succeed. A misspelled
keyword or an invalid value reaches adopters unnoticed. The next specs
in this series change GitLab output a lot.

## Constraints

- **Output shape does not change.** Apart from the replaced `@latest`
  versions, every generated CI file stays byte-identical. Job names,
  steps, images, variables and comments are unchanged. This spec
  changes where the values come from, not what is generated.
- **Toolchain versions do not change.** Go, Task, the Task checksum,
  golangci-lint, Node and Python keep their current values.
- **Scope of the table** (decided with the user): the generated CI
  templates and both conformance files (`conformance.yml`,
  `gitlab-ci.vibe.yml`). Taskfiles, `doctor` and this repository's own
  hand-written workflows are out of scope.
- **Principle 3 / spec 0022.** Only the conformance pieces run `vibe`,
  and removing VibeConform is still deletion only.
- **Spec 0019 (drift).** An adopting repository picks up the pinned
  versions through a normal `vibe sync`, as an update from a moved
  standard, not as local drift.
- **Dependencies.** No new production dependency. The schema checker
  runs only in this repository's CI, through `uvx`, at a pinned version.
- **Dependency direction** (`docs/architecture/overview.md`): the table
  lives under `internal/module` and depends on nothing new.

## Assumptions

Verified on 2026-10-07:

- `check-jsonschema` 0.38.2 ships GitLab's CI schema as
  `--builtin-schema vendor.gitlab-ci`. `--data-transform gitlab-ci`
  handles GitLab's YAML tags.
- The current generated GitLab output passes that check:
  - `.gitlab-ci.yml` and `.gitlab-ci.vibe.yml`
  - for a `gitlab` copy of `examples/monorepo`, generated by a vibe
    built from `main` at `5223f2b`
- The check rejects a misspelled job keyword (`alow_failure`) and an
  invalid `cache:policy` value. Both were tried on edited copies.

Not verified:

- The schema lags GitLab, and may reject a keyword GitLab already
  accepts. This is why the checker version is pinned and bumped on
  purpose.
- The schema checks keywords and value shapes. It does not check how
  `include:`, `extends:` or `rules:` resolve. That is issue #74.
- Exact versions to pin for `goimports` (`golang.org/x/tools`),
  `govulncheck` and `actionlint`. The latest releases on the day of
  implementation are used and recorded in the table.

## Desired Behavior

### 1. One table

- Every toolchain version that appears in a generated CI file comes
  from a single table in the source:
  - Go, Task, the Task release checksum, golangci-lint, Node and Python
  - the newly pinned `goimports`, `govulncheck` and `actionlint`
- No CI or conformance template contains one of these values as a
  literal.
- Changing a value in the table changes every generated CI file that
  uses it, and nothing else has to be edited.
- The Task version and its checksum sit next to each other in the
  table, with a comment saying they change together.
- A comment on the table states the bump practice: when `GO_VERSION` is
  bumped, the tool pins (`goimports`, `govulncheck`, `actionlint`,
  golangci-lint) are bumped in the same change, to versions that build
  with that Go. Detecting stale pins automatically is issue #75.

### 2. No floating tools

- No generated CI file installs a tool `@latest`.
- `goimports`, `govulncheck` and `actionlint` are installed at the
  versions in the table, with the same pinning style as golangci-lint.

### 3. A test that fails on a missed pin

A test renders every CI and conformance file for every standard and
provider that emits one:
- `prod-go`, `prod-ts`, `prod-py`
- `prod-mono` under `github` and under `gitlab`

It fails in two cases:
- a rendered file contains a version different from the table's
- a rendered file contains `@latest`

This test replaces `TestVersionsMatchGitHub`.

### 4. GitLab schema check in CI

- The `monorepo-gitlab` job in `.github/workflows/examples.yml` checks
  the generated `.gitlab-ci.yml` and `.gitlab-ci.vibe.yml` against
  GitLab's CI schema, with `check-jsonschema` at a pinned version.
- A schema error fails the job.
- The step comment says what the check covers (keywords and value
  shapes) and what it does not (include and rules resolution, a real
  run; see #74).

### 5. Repository and examples

- This repository, `examples/python`, `examples/typescript` and
  `examples/monorepo` are synced with the rebuilt binary.
- The only differences in their generated CI files are the replaced
  `@latest` lines.

### 6. Documentation

- `docs/usage.md`, "CI provider": the generated CI pins every tool, and
  bumping a pin takes a new VibeConform release. A pinned `govulncheck`
  still reports new vulnerabilities.
- `GLOSSARY.md` (written during the 2026-10-07 session) is committed
  with this spec.

## Non-goals

- **Changing any toolchain version.** Go, Task, golangci-lint, Node and
  Python keep their values. Only the `@latest` tools gain pins.
- **Pins outside CI.** Taskfiles, `doctor`'s tool list, and
  `.github/workflows/examples.yml`'s own `env:` pins. The schema-check
  step is the one change in `examples.yml`.
- **GitHub Action SHAs** (`actions/checkout`, `setup-go`, …). They are
  pinned already, and Dependabot handles them.
- **Restructuring templates.** Partials and `extends:` belong to the
  next spec, and output shape is frozen here.
- **Schema-checking GitHub workflows.** actionlint already covers them.
- **A real GitLab run** (issue #74).
- **Automatic detection of stale pins** (issue #75). A pinned
  `govulncheck` still reads the live vulnerability database, so
  vulnerabilities published later are still reported.
- **An ADR.** The table is easy to reverse and involves no real
  trade-off (decided with the user).

## Acceptance Criteria

- [x] **One source.** No template under `internal/module` (CI modules
      and conformance) contains a version literal that the table
      defines, nor `@latest`. A test checks this on the template
      sources.
- [x] **Rendered agreement.** For each of `prod-go`, `prod-ts`,
      `prod-py`, `prod-mono`+`github` and `prod-mono`+`gitlab`, every
      generated CI and conformance file uses exactly the table's
      versions. Changing one table value in a test makes every file
      that uses it change.
- [x] **Shape unchanged.** For each case above, the generated CI files
      differ from those generated at `main` (`5223f2b`) only in lines
      that had `@latest`. A golden or diff test shows this.
- [x] **Task checksum.** `TASK_SHA256` in the GitLab output comes from
      the table entry next to `TASK_VERSION`.
- [ ] **Schema check runs.** The `monorepo-gitlab` job runs
      `check-jsonschema` at a pinned version with
      `--builtin-schema vendor.gitlab-ci --data-transform gitlab-ci` on
      `.gitlab-ci.yml` and `.gitlab-ci.vibe.yml`, and it is green.
- [x] **Schema check fails when it should.** Checked once by hand and
      recorded in the PR: a copy with a misspelled keyword fails the
      step.
- [ ] **Repository checks.** This repository and `examples/` are
