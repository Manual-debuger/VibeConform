# Spec 0040: The CI Floor, and an Environment Seam for GitLab Jobs

Status: accepted and implemented (2026-10-05); real GitLab pipeline
UNVERIFIED. Implementation plan:
`docs/plans/0040-ci-floor-environment-seam.md`. Open questions resolved
with the user: audit checks the seam file's shape, the file is named
`.gitlab-ci.defaults.yml`, and an image-registry prefix is deferred until
an adopter needs it. Builds on spec 0038 and ADR 0019 (CI provider,
GitLab child-pipeline seam), ADR 0003 (resource ownership) and ADR 0009
(extending a generated file without owning it). Records its decision in
ADR 0021. First case: issue #65.

## Problem

VibeConform owns every byte of the generated GitLab jobs, and a project
cannot change any of them: ADR 0019 rejected `include: local`, and a
child pipeline cannot touch parent jobs. That protects the jobs the
standard requires, but it also protects settings that are not the
standard's business, only the runner's:

1. **Cache policy (issue #65).** Every job uses the default
   `pull-push`, so every merge request pipeline re-uploads an unchanged
   cache. The reporter's Go job spent 22 s of 90 s doing that. Their
   hand-written file used to set `policy: pull` on merge request
   pipelines.
2. **Runner selection.** A self-managed GitLab whose runners only take
   tagged jobs cannot run the generated jobs at all. There is no way to
   add `tags:`.
Every such setting becomes an upstream issue and a VibeConform release.
That does not scale across GitLab installations.

The guard has limits anyway. A GitLab maintainer can already set a
project CI/CD variable that empties a test run (for example
`PYTEST_ADDOPTS=-k nothing`). VibeConform has never been able to
guarantee that CI gates merges (spec 0022). The byte-for-byte guard
stops accidental drift. It does not stop someone determined to get
around it.

## Constraints

- **Backward compatibility.** A project that adds no seam file and sets
  no new variable gets the same pipeline behaviour as today. The
  generated bytes may change (spec 0038's §4 output is not frozen), but
  every job runs the same commands, in the same images, with the same
  cache key and paths, and with `pull-push`.
- **Principle 1 / ADR 0009.** A seam must not let a project weaken what
  a required job runs or whether its result counts, unless the gap is
  documented.
- **Principle 3 / spec 0022.** Only the conformance pieces run `vibe`.
  Removing VibeConform is still deletion only.
- **ADR 0003.** VibeConform never writes a project-owned file.
- **ADR 0012.** Manifest decoding stays strict. This spec adds no
  `vibe.yaml` key.
- **Provider scope.** `ci.provider: gitlab` in `prod-mono` only, as in
  spec 0038. The GitHub output does not change.

## Assumptions

Verified against docs.gitlab.com (2026-10-04):

- `default:` accepts `after_script`, `artifacts`, `before_script`,
  `cache`, `hooks`, `id_tokens`, `image`, `interruptible`, `retry`,
  `services` and `tags`. "Default configuration does not merge with job
  configuration. If the job already has a keyword defined, the job
  keyword takes precedence."
- Global defaults are not passed to downstream (child) pipelines.
- `cache:policy` and `tags` accept CI/CD variables.
- `workflow:rules:variables` override top-level `variables`.
- Cache keys get a `-protected` suffix when the pipeline runs for a
  protected ref, or when a user with the Maintainer or Owner role started
  it. Otherwise they get `-non_protected`. "Use separate caches for
  protected branches" is on by default. So a Developer's merge request
  pipeline cannot read the default branch's cache, and a Maintainer's
  can.

Not verified (each needs a real pipeline, acceptance 9):

- An included file's `default:` applies to jobs in the main
  `.gitlab-ci.yml` and in other included files.
- `inherit: default: false` on a trigger job avoids errors from
  defaults the trigger job does not support (for example `tags`).
- A project CI/CD variable overrides both a top-level `variables:`
  entry and a `workflow:rules:variables` entry of the same name.
- GitLab uploads a `pull-push` cache even when the key was a hit. The
  reporter observed this. The docs do not say.

## Desired Behavior

### 1. The floor

Each required GitLab job (one per component, and `conformance:audit`)
has two kinds of keys:

- **Contract keys** decide what the job runs and whether its result
  counts: `stage`, `image`, `needs`, `rules`, `allow_failure`,
  `before_script`, `script`, `interruptible`, the declared `variables`,
  and the `cache` key and paths. They stay generated and declared on
  every job, and no seam can change them. (`image` is contract for now:
  the toolchain version is part of the standard. A registry prefix is
  deferred until an adopter needs one.)
- **Environment keys** decide where and how fast the job runs: runner
  `tags`, `retry`, `services`, `artifacts`, `after_script`, `hooks`,
  `id_tokens` and the cache policy. The project sets them through the
  seams in §2 and §3.

The workflow rules, the `include` of `.gitlab-ci.vibe.yml` and the
`local` child-pipeline job are also contract.

### 2. Seam: `.gitlab-ci.defaults.yml`

- `.gitlab-ci.yml` includes `.gitlab-ci.defaults.yml` with
  `rules: exists` on that path, after `.gitlab-ci.vibe.yml`. When the
  file is absent, the include does nothing.
- The file is project-owned. VibeConform never creates or writes it.
- Its only top-level key may be `default:`. Under `default:`, a project
  can set any keyword GitLab accepts there. A keyword that a required
  job already declares has no effect on that job, by GitLab's
  precedence rule. In practice that leaves the environment keys.
- **`vibe audit` checks the file's shape.** When the file exists, it
  must parse as a YAML mapping whose only key is `default`. Any other
  top-level key (a job, `variables`, `include`, `workflow`, …) is
  non-conformant: audit exits 2 and names the file and each extra key.
  An absent file is conformant. Audit checks nothing under `default:`.
- The generated `local` job declares `inherit: default: false`, so
  project defaults never reach the trigger job. The child pipeline sets
  its own defaults in `.gitlab-ci.local.yml`.

### 3. Seam: a variable for the cache policy

The cache policy sits inside `cache:`, which every component job
declares, so `default:` cannot reach it. It becomes a CI/CD variable
with a default in the generated file, which a project overrides under
Settings > CI/CD > Variables:

| Variable | Default | Effect |
|---|---|---|
| `VIBE_CACHE_POLICY` | `pull-push` | each component job's `cache:policy` |

### 4. Merge request cache policy (issue #65)

The generated `workflow:rules` gain one rule, placed before the plain
merge request rule:

```yaml
- if: $CI_PIPELINE_SOURCE == "merge_request_event" && $VIBE_MR_CACHE_POLICY == "pull"
  variables:
    VIBE_CACHE_POLICY: pull
```

- A project opts in by setting the CI/CD variable
  `VIBE_MR_CACHE_POLICY=pull`. Its merge request pipelines then only
  read caches. Every other pipeline still uses `pull-push`.
- Without the variable, nothing changes. The default is opt-in because
  of the protected-cache rule: on a default-configured project, a
  Developer's merge request pipelines read only `-non_protected` caches,
  and only merge request pipelines write those. With `pull` they would
  never get a cache.
- Which pipelines run, and the de-duplication of branch and merge
  request pipelines, do not change.

### 5. Documentation

- `docs/usage.md`, "CI provider":
  - the floor in plain terms;
  - `.gitlab-ci.defaults.yml`, with an example that sets runner `tags`;
  - the two variables (`VIBE_CACHE_POLICY`, `VIBE_MR_CACHE_POLICY`);
  - the protected-cache caveat with its role nuance, and when turning
    on `VIBE_MR_CACHE_POLICY` helps;
  - the known gaps in §6.
- A new ADR 0021 records the floor/environment split, the `default:`-only
  include and the audit shape check. It amends ADR 0019 decision 4: a
  limited include is now accepted next to the child pipeline.

### 6. Documented gaps (not closed)

- Project CI/CD variables can still change how tools behave (for
  example `PYTEST_ADDOPTS`), as they could before this spec.
- `default: retry` can turn a flaky failure into a pass. That is the
  project's choice.
- `default: hooks` and `default: services` run project code next to a
  required job. They can make it fail, which is visible, but they also
  share its environment.

The guard stops accidental drift, not someone set on getting around it.

## Non-goals

- **GitHub environment seams** (for example `runs-on` from `vars`).
  GitHub already lets a project add workflows freely. Runner selection
  there is a follow-up if someone asks for it.
- **A `vibe.yaml` setting for any of this.** Environment settings belong
  in GitLab's own settings or in the project-owned file, not in the
  manifest.
- **Checking the values under `default:`**, or the values of the
  variables.
- **Making `pull` the merge request default**, or scheduled
  cache-warming pipelines.
- **An image-registry prefix** (registry mirror, dependency proxy).
  Runner-level Docker mirrors already cover Docker Hub. Add a variable
  when an adopter needs it.
- **Changing `prod-go`, `prod-ts` or `prod-py`**, which still offer
  only GitHub.

## Acceptance Criteria

- [x] **Unchanged behaviour by default.** With no seam file and no new
      variable set, every generated job has the same script, image name
      and tag, cache key and paths as before, with the policy resolving
      to `pull-push` (structural test on the parsed YAML).
- [x] **Contract keys stay declared.** Every component job and
      `conformance:audit` declares every §1 contract key. A test lists
      them so a template change can't silently drop one.
- [x] **Defaults include.** `.gitlab-ci.yml` includes
      `.gitlab-ci.defaults.yml` with `rules: exists` on its own path,
      after the `.gitlab-ci.vibe.yml` include. `local` declares
      `inherit: default: false`.
- [x] **Variable.** Every component job's `cache:policy` is
      `$VIBE_CACHE_POLICY`, and the top level sets it to `pull-push`.
- [x] **MR rule.** The opt-in rule comes before the plain merge request
      rule, matches only merge request pipelines with
      `VIBE_MR_CACHE_POLICY == "pull"`, and sets only
      `VIBE_CACHE_POLICY: pull`. The other workflow rules are unchanged.
- [x] **Audit shape check.** In a temp `prod-mono` + `gitlab`
      repository:
      - an absent `.gitlab-ci.defaults.yml` is conformant;
      - a file with only `default:` (any content under it) is
        conformant;
      - a file with an extra top-level key (`api:`, `variables:`,
        `include:`) is non-conformant, exits 2 and names each key;
      - a file that is not a YAML mapping is non-conformant;
      - `sync` never creates, changes or deletes the file.
- [x] **Scope.** Under `github` and `none`, the output is byte-identical
      and audit never reads `.gitlab-ci.defaults.yml`.
- [x] **Repository checks.** `examples/` and this repository are
      conformant after the sync. `task verify` and `task audit` pass.
- [ ] **Real integration (a separate ledger line).** On a GitLab
      project holding a `gitlab` copy of `examples/monorepo`:
      - the pipeline is green with no seam set;
      - a `.gitlab-ci.defaults.yml` setting `tags:` routes every
        component job and `conformance:audit` to the tagged runner, and
        the `local` child pipeline still starts;
      - with `VIBE_MR_CACHE_POLICY=pull`, a merge request job logs that
        it is not uploading the cache, and a default-branch job uploads
        it.
- [x] **Documentation.** §5 is written, including ADR 0021.

## Resolved questions

1. **Audit the seam file's shape: yes.** Auditing is a new kind of
   check: VibeConform reads a file it does not own. Without it, the
   include reopens the hole ADR 0019 closed (a project file could
   deep-merge `variables` or `allow_failure` into a required job).
2. **Image-registry prefix: deferred** (see Non-goals).
3. **File name: `.gitlab-ci.defaults.yml`.** It says what the file may
   hold, and it sits next to `.gitlab-ci.local.yml` and
   `.gitlab-ci.vibe.yml`.
